# Deployment and security

Backend and integration: IamAtomic

Web-Based Social Engineering Awareness Platform for Remote Workers
Group 4 | Capstone 2

## What changed for going live

The backend now serves the built Vue app from its own origin. That means one
service, one URL, and no cross origin requests between the frontend and the
API. Locally you still run the two separately so Vite can hot reload.

| | Local | Deployed |
|---|---|---|
| Frontend | `npm run dev` on port 5173 | built to `dist/`, served by the API |
| API | `npm start` in `backend-node` on 3000 | same process, same port |
| URLs | typing `/login` hits the old static file | works correctly, `dist` has no stale HTML |

That last row is worth knowing: the stale HTML files that shadow Vue routes
during development are not in the production build, so direct links behave
properly once deployed.

## Security work

### The API was open to every website on the internet

`app.use(cors())` with no options allows any origin. A malicious site could
have called this API using a logged in user's browser and their session.

It now accepts only the origins named in `CORS_ORIGINS`, plus the local dev
server when not in production. Verified: an allowed origin gets `200`, an
unknown one gets `403`.

### Secrets no longer fall back to hardcoded values

The previous code did this:

```js
const JWT_SECRET = process.env.JWT_SECRET || 'dev-secret-change-in-production';
```

Convenient locally, but this repository is public. Anyone could read that
fallback and, if a deployment ever started without the variable set, forge a
token for any account including an administrator. The database password had
the same pattern.

`config/env.js` now refuses to start in production when `JWT_SECRET`,
`DB_PASSWORD` or `CORS_ORIGINS` are missing, and rejects a `JWT_SECRET`
shorter than 32 characters. Local development is unaffected.

Generate a real one with:

```
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

### Brute force protection

bcrypt makes each password guess slow to verify, but nothing stopped the
guesses being made. Per IP limits now apply, verified by sending 25 rapid
login attempts: the first 20 returned `401`, the rest `429`.

| Endpoint group | Limit |
|---|---|
| login, register, forgot and reset password | 20 per 15 minutes |
| verify and resend one time code | 10 per 15 minutes |
| everything else under `/api` | 300 per 15 minutes |

### Other hardening

- **Security headers** through helmet: clickjacking, MIME sniffing and
  referrer leakage. Verified present in the response.
- **`x-powered-by` removed**, so the stack and version are not advertised.
- **Request body capped at 100kb**, so one oversized request cannot exhaust
  memory.
- **Error details stay in the server log.** They can name tables, columns and
  file paths, so the browser only ever receives a generic message.
- **Health check queries the database**, so a host restarts the service when
  MySQL is unreachable rather than leaving a broken instance running.
- **TLS for the database** via `DB_SSL=true`, which hosted providers require.

## Deploying

The app needs somewhere that runs Node and a MySQL database. Render's free
tier covers the Node side but only offers PostgreSQL, so MySQL comes from a
separate provider.

### 1. Database

Create a MySQL database with any provider, then run the three files in
`backend-node/sql/` against it in order:

```
01-jyan-base-schema.sql
02-backend-additions.sql
03-seed.sql
```

Keep the host, port, user, password and database name.

### 2. Web service

Connect the repository to Render. `render.yaml` describes the service, so the
build and start commands are already set:

- Build: `npm install && npm run build`
- Start: `npm start`
- Health check: `/api/health`

### 3. Environment variables

Set these in the dashboard. `JWT_SECRET` is generated by Render, so it never
passes through a chat or a commit.

| Variable | Value |
|---|---|
| `NODE_ENV` | `production` |
| `JWT_SECRET` | generated by Render |
| `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` | from your MySQL provider |
| `DB_SSL` | `true` |
| `CORS_ORIGINS` | the deployed URL, e.g. `https://se-aware.onrender.com` |

`CORS_ORIGINS` must match the deployed URL exactly, scheme included. If it is
wrong the site loads but every API call is refused.

### 4. Check it

Open `/api/health`. A healthy response is:

```json
{"status":"ok","database":"connected"}
```

`degraded` means the database credentials are wrong. If the service will not
start at all, the logs will name the missing variable directly, which is the
guard doing its job.

## Free tier behaviour worth knowing

Free services sleep after about 15 minutes of inactivity, and the first
request afterwards takes roughly 30 to 60 seconds while it wakes.

Open the link yourself five minutes before any demonstration. It is a small
thing that avoids a long silence in front of a panel.

## Quiz results now save to the account

Finishing a module quiz while signed in records the attempt, so it appears in
quiz history and marks the module complete on the dashboard. Guests can still
take every quiz; their score simply stays in the tab, and the results page
offers a link to log in rather than failing silently.

The results are flagged as saved in sessionStorage once recorded, so
refreshing the results page does not log the same attempt again. Verified by
refreshing twice and confirming the database still held one row.

### A slug mismatch this uncovered

The database seed still used the module names from before the content pass, so
two of them no longer matched the frontend:

| Frontend | Database (old) |
|---|---|
| `quishing` | `phishing` |
| `essential-safe-practices-remote-environments` | `safety-practices` |

Recording an attempt for either would have failed with "Module not found".
`03-seed.sql` now matches the content, since that is what was finalised.

**If your database was created before this change**, re-run the three SQL
files, or update the two rows directly:

```sql
UPDATE module SET slug = 'quishing', module_title = 'Quishing'
  WHERE slug = 'phishing';

UPDATE module SET slug = 'essential-safe-practices-remote-environments',
                  module_title = 'Essential Safe Practices for Remote Environments'
  WHERE slug = 'safety-practices';
```
